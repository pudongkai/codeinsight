# CodeInsight 网页配置技术方案：在网页里配置模型服务、选择仓库，分析结果的保存与更新

开发状态: DONE
方案评审: 通过（2026-11-13）
需求来源: 2026-11-13 用户需求：“`codeinsight serve` 启动网页后，在网页中配置模型服务（provider、baseUrl、model、apiKey），在网页中指定要分析的仓库”；追加：“分析的结果能固化吗？不需要每次分析同一个项目都从头分析吧？还有如何更新也要考虑”
作者: dongkai@zbyte-inc.com　　日期: 2026-11-13

## 1. 背景与目标

现在用 CodeInsight 要先在命令行里设好环境变量（`CODEINSIGHT_LLM_PROVIDER`、`CODEINSIGHT_LLM_API_KEY` 等），再在仓库目录下执行 `codeinsight serve`；换一个仓库或改模型配置都要重启 serve。网页上没配置模型时只显示一段环境变量说明。另外，用户不清楚再次打开同一个仓库时是否会从头分析，改了代码之后网页也不会提示索引已经过时。

做完后要达到：

1. `codeinsight serve` 不带 `--repo` 时：当前目录在 git 仓库里就照旧打开它（兼容现有用法）；不在时也能启动，stdout 那行 JSON 的 `repo`、`dataDir` 为 `null`，打开网页看到“选择仓库”页面，输入本机路径或点最近使用的仓库后开始建索引，之后和现在的页面一样。带 `--repo` 时行为和现在一致。新增 `--lock-repo`：锁定启动时的仓库，网页不显示切换入口、切换接口返回 409；JetBrains 插件启动参数加上 `--lock-repo`（插件只改这一处）。
2. 网页顶栏能切换当前仓库。没有任务在跑时切换立即生效；有建索引、概览、审查、问答任务在跑时，接口返回 409 并列出这些任务，网页提示等它们结束（建索引和问答可以“取消并切换”）。切回之前打开过的仓库时直接复用已有快照和概览，不从头分析。
3. 网页里有“模型服务设置”对话框：provider、baseUrl、model、apiKey，保存到用户级文件 `~/.codeinsight/settings.json`（权限 600），保存后不用重启 serve，下一次请求就用新配置；页面上显示每一项的值来自用户设置、环境变量、仓库配置还是默认值。API Key 不回传给网页，只显示“已设置（末 4 位 xxxx）”。“测试连接”按钮用表单里的配置发一个最小请求，显示成功或失败原因。
4. `codeinsight overview`、`ask`、`review`、`mcp` 等命令和 serve 读同一份用户设置，在网页里配好一次，命令行也能用。
5. 多个浏览器标签页打开同一个 serve 时，一个标签页切换了仓库，其他标签页在一个轮询周期（5 秒）内发现并刷新到新仓库；旧标签页还没刷新时发出的请求被拒绝（409 `repo_changed`），不会读写到新仓库的数据。
6. 网页上看得出分析结果是复用的：顶栏显示“索引建于 xx、基于提交 abc1234（含未提交改动）”，复用已有索引时标明“复用已有索引”；概览卡片显示“生成于 xx、基于提交 abc1234（含未提交改动）”。
7. 改了代码后，网页在约 10 秒内提示“代码已变化，索引不是最新的”，并提供“更新索引”；设置里可以打开“检测到变化后自动更新索引”（默认关）。概览只提示过期，始终由用户手动更新。
8. “打开仓库”对话框有“选择目录…”按钮：由 serve 弹出系统原生的选择文件夹窗口（macOS、Linux 桌面、Windows），选中后绝对路径填进输入框；系统不支持时只保留输入框和最近使用列表。
9. 增量建索引：新快照里内容没变的文件复用之前的提取结果，快照源码目录里内容没变的文件用硬链接代替复制；只改了非 Python 文件（如 README）时直接复用上一个快照的调用关系，不跑 scip-python。增量建出的索引和全量重建的结果完全相同（文件、符号、入口、调用边逐行一致）。

## 2. 范围

**本次要做：**
- core：用户设置文件（读写、权限、最近仓库列表、自动更新开关）；`loadConfig` 合并用户设置并给出每个 LLM 配置项的来源
- core：增量建索引（按文件内容的提取结果缓存、快照源码目录硬链接、Python 文件都没变时复用调用边）；工作区快照“是否含未提交改动”的判断
- server：当前仓库上下文可替换（无仓库、切换、关闭旧 Store）；仓库选择、模型设置、测试连接、通用设置接口；弹出系统选择文件夹窗口的接口；`/api/status` 增加仓库标识、代码变化检测；请求带仓库标识时检查是否过期；自动更新索引
- cli：`serve` 不传 `--repo` 且当前目录不在 git 仓库里时以“无仓库”启动；stdout JSON 的 `repo`、`dataDir` 可为 null；新增 `--lock-repo`；打开仓库时更新最近列表
- JetBrains 插件：`ServeProcess.kt` 启动参数加 `--lock-repo`
- core：建快照支持中止信号（`AbortSignal`），用于“取消并切换”
- web：选择仓库页、顶栏仓库切换入口和设置入口、模型服务设置对话框、问答页和概览生成弹窗的“去设置”引导、多标签页同步、分析结果来源和代码变化提示
- 测试：core、server、cli 单测，web 组件测试和 Playwright；插件内检查项写进 `plugins/jetbrains/MANUAL_CHECKS.md`

**本次不做：**
- 同时打开多个仓库（见 4.6）
- 取消正在跑的概览和审查任务（`OverviewJobs`、`ReviewJobs` 和 core 的 `runOverview`、`runReview` 都没有中止能力，加中止要改 core 的整条流程）；有这两类任务时只能等它们结束再切换
- 服务端目录浏览接口和网页里的目录树（选择目录用系统原生窗口，见 4.6）；从网页克隆远程仓库
- 网页里修改费用和发送相关的上限（`sendSource`、并发数、确认阈值、问答轮数），这些仍按现有规则从仓库配置和环境变量读
- 在网页里修改仓库配置文件 `codeinsight.config.json`
- API Key 存进系统钥匙串（macOS Keychain 等），本次只用权限 600 的文件
- 不打开网页时的代码变化检测（变化检测由网页轮询 `/api/status` 触发；没有网页打开时不检测、不自动更新）
- scip-python 增量运行（原因见 4.4.6）
- `llm-cache` 目录的自动清理：缓存文件按内容 hash 命名，读取时不更新时间，没有“最后使用时间”可用；需要清理时可以直接删除 `<dataDir>/llm-cache/`（下次生成概览会重新请求）。本次只在 4.4.6 里写清楚
- 相似检测结果缓存（`/api/similar` 每次实时计算，耗时不在本需求范围）
- MCP（`codeinsight mcp`）切换仓库：MCP 仍是一个进程一个仓库
- 多个 serve 进程同时改用户设置时的加锁（后写的覆盖先写的，见风险）

## 3. 现状分析

**serve 启动与仓库绑定**
- `packages/cli/src/commands/serve.ts`：`parseServeArgs` 里 `--repo` 的默认值是 `'.'`（不是必填，现在不传就用当前目录）；`startServe` 调 `openWorkspace(args.repo, args['data-dir'])`，再 `startHttpServer({ workspace, port, staticDir })`，然后在 stdout 输出一行 `{port, token, url, repo, dataDir}`，`repo`、`dataDir` 是绝对路径。`stop` 里关闭 Store。
- `packages/cli/src/commands/workspace.ts:openWorkspace`：`repoRoot(path.resolve(repoArg))`（`git rev-parse --show-toplevel`，传子目录得到仓库根目录）→ `loadConfig(repo, { dataDir })` → `initDataDir` → `checkPyrightExclude` 的提示写 stderr → `new Store(layout.dbPath)`。`mcp.ts`、`overview.ts`、`ask.ts`、`review.ts` 等命令都用它。
- `packages/server/src/workspace.ts:ServerWorkspace {repo, config, layout, store, resolver?}`。
- `packages/server/src/http/server.ts:startHttpServer`：建 `AppContext {ws, indexJobs: new IndexJobs(ws), reviewJobs: new ReviewJobs(ws), overviewJobs: new OverviewJobs(ws), askRuns: new AskRuns(), staticDir, touched: new Map()}`；`indexOnStart !== false` 时 `indexJobs.start('startup')`；每 5 分钟 `indexJobs.touchCurrent()` 防止当前快照被清理；`close({drain})` 等审查、索引、概览结束并中止问答。`RunningHttpServer` 暴露的 `indexJobs`、`reviewJobs`、`overviewJobs` 在仓库里没有调用方。
- `packages/server/src/http/context.ts`：`AppContext`、`RequestContext {req, res, url, params, app, logFields}`、`Route.method` 只有 `GET | POST | DELETE`（没有 PUT）。路由里到处直接用 `ctx.app.ws`（`routes/{status,overview,chat,entries,symbols,similar,source}.ts`、`http/snapshot.ts`）。

**各任务类的中止能力**（`packages/server/src/jobs/`）
- `index-jobs.ts:IndexJobs`：同时只跑一个，`current()` 返回最近一次成功的快照，`drain()` 等任务结束，没有取消方法。建索引里最耗时的是 scip-python 子进程，core 有进程级的 `killActiveScipProcesses()`（`packages/core/src/scip/runner.ts:107`，结束本进程所有 scip-python 子进程），被结束后 `runResolver` 把快照标为 `resolver_status=failed`，下次打开同一内容时 `buildOrReuse` 会只重跑解析。但它只能结束已经启动的子进程：建索引还在复制文件、提取阶段时调用它没有效果，提取完仍会启动 scip-python。`buildSnapshot` 没有中止参数。`IndexJobs` 已有私有字段 `running`。
- `overview-jobs.ts:OverviewJobs`：`runningId` 是私有字段，没有取消；构造时 `failInterrupted()`。`core/src/store/overviews.ts:failDeadRunning` 只改“pid 已不存在、或 pid 是本进程但不是本进程开始的”running 记录（`isRunningAlive`），CLI 进程正在跑的概览不会被改。
- `review-jobs.ts:ReviewJobs`：用 `PendingSet` 记录进行中的任务，没有取消；构造时 `failInterruptedReviews()`（`core/src/store/db.ts:453`）：跳过 pid 是其他存活进程的记录，但 **pid 等于本进程的 running 记录一律改为 failed**——同一个 serve 进程里再次构造 `ReviewJobs` 时，会把本进程别的上下文正在跑的审查误标失败。审查也会调 `buildSnapshot`（会跑 scip-python）。
- `ask-runs.ts:AskRuns`：每个问答有 `AbortController`，有 `cancel(sessionId)` 和 `drain()`（全部中止并等回答保存为 cancelled）。

**配置**（`packages/core/src/config/index.ts`）
- `loadConfig(repo, {dataDir, env})`：优先级 命令行 > 环境变量 > `<repo>/codeinsight.config.json` > 默认值。数据目录 `opts.dataDir ?? env.CODEINSIGHT_DATA_DIR ?? file.dataDir ?? '.codeinsight'`，按仓库根目录解析。
- `resolveLlm`：provider、model 来自环境变量或仓库配置；`baseUrl`、`apiKey` 只读环境变量（`ENV_ONLY_LLM_KEYS`，仓库配置里写了会被忽略并给出 `config_llm_key_ignored` warning）；apiKey 依次取 `CODEINSIGHT_LLM_API_KEY`、按 provider 取 `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`；anthropic 没给 model 时用 `DEFAULT_ANTHROPIC_MODEL`，openai-compatible 缺 model 时返回 `llmProblem`。
- `costLimits`：`sendSource`、源码片段、并发、确认阈值、问答上限“仓库配置只能调严，放宽只能用环境变量”。
- LLM 客户端每次按配置现建：`packages/core/src/llm/setup.ts:llmClientFromConfig`；聊天路由 `routes/chat.ts` 的 `askClient(ctx.app.ws.config)`。各任务在开始时从 `this.ws` 解构出 `config`（`ReviewJobs.run`、`OverviewJobs.options`、`IndexJobs.run`），所以替换 `ws.config` 对象后，已开始的任务继续用旧配置。
- 默认 baseUrl：anthropic `https://api.anthropic.com`，openai-compatible `https://api.openai.com/v1`（`packages/core/src/llm/index.ts:60`）。

**数据目录和快照**（`packages/core/src/store/data-dir.ts`、`packages/core/src/snapshot/build.ts`）
- 数据目录默认 `<repo>/.codeinsight/`：`index.db`、`snapshots/<contentKey>/`、`scip/<contentKey>.scip`、`llm-cache/`、`overview/partition.json`、`locks/`。`initDataDir` 会在数据目录写 `.gitignore`（内容 `*`）。库里没有记录“属于哪个仓库”。
- 工作区快照键 `packages/core/src/git/index.ts:workingContentKey`：`HEAD sha` + 相对 HEAD 改动的文件（含未跟踪文件）的路径和内容的 sha1 前 16 位。没有改动时后缀是空输入的 sha1 前 16 位 `da39a3ee5e6b4b0d`。计算只读改动的文件，代价和改动量成正比。
- `buildSnapshot`：`reusable()`（`build.ts:71`）内容键相同且提取、解析都成功就整体复用，不跑任何分析；否则加快照锁后 `buildLocked`（`build.ts:179`）：`prepareWorking` 先删掉快照目录，把清单里支持语言的文件和项目配置**逐个复制**到 `snapshots/<contentKey>/`，然后 `readFiles` **再从工作区读一遍全部文件**算 `content_hash`，`extractPythonFiles` 对全部 Python 文件重新解析，最后 `runResolver` 对整个快照目录跑 scip-python（结果按 contentKey 缓存在 `scip/`）。`files.content_hash` 只写入，没有被用来复用。
- 提取不是纯按文件的：`extractPythonFiles`（`packages/core/src/extract/index.ts:29`）先逐个文件 `extractPythonFile`，再跨文件做 `resolveDjangoEntries`（urls.py 的路由指向别的文件里的视图）和 `resolveModels`（按跨文件继承判断模型类，会改写 `symbol.modelKind`）。跨文件这两步需要 `ExtractedFile` 里的 `classes`、`baseVars`、`imports`、`djangoRoutes`，从库里还原的文件（`restoreExtractedFile`）没有这些。
- 符号 id = sha1(symbol_key) 前 16 位，同一函数在不同快照里 id 相同；`edges` 行只有 `src_id`、`dst_id`、`path`、`line`、`col` 等，不含快照特有的值，可以整批复制到新快照。
- `cleanupSnapshots`：保留最近使用的 8 个快照（`KEEP_SNAPSHOTS`），10 分钟内用过或持有锁的不删。
- 概览存在 `overviews` 表，网页打开时直接读最近一次；`overviewStale`（`packages/server/src/jobs/overview-jobs.ts:19`）按 content_key 和当前快照比较，网页 `web/src/overview/SystemCard.tsx` 显示过期提示和“更新概览”。模块划分记录和 LLM 缓存在重新生成时复用。审查保留 20 条，问答保留 50 个会话。
- 改了代码之后，只有 serve 启动、点“重新建索引”或 MCP 调用时才建新快照；在这之前当前快照不变，概览也不会显示过期。

**用户级配置**：项目里没有任何用户级文件（`~/.codeinsight` 没有被使用），也没有 `CODEINSIGHT_HOME` 之类的变量。`packages/core/src/util/atomic-file.ts:writeFileAtomic` 先写临时文件再改名，但不支持指定文件权限（临时文件按 umask 创建，一般是 644）。

**鉴权**（`packages/server/src/http/auth.ts`、`server.ts:gate`）：只监听 127.0.0.1；`newToken()` 随机 token，首页 `?token=` 换成 HttpOnly cookie `ci_<port>` 后重定向；也接受 `Authorization: Bearer`；`hostAllowed` 检查 Host 和 Origin 必须是 `127.0.0.1:<port>` / `localhost:<port>`。请求日志 `http_request` 只记方法、路径、状态、耗时、查询参数（去掉 token）和路由追加的 `logFields`，不记请求体。

**Web**（`packages/web/src/`）
- `app/App.tsx`：概览、浏览、问答、审查四个标签，无路由；`app/useStatus.ts` 读 `/api/status`，**只在建索引期间轮询**（`needsPolling`），索引建好后不再轮询；`app/StatusBar.tsx` 显示仓库路径、索引时间、建索引进度和“重新建索引”。
- `chat/ChatPage.tsx:AskGate`：未配置 LLM 时显示 `overview/GenerateDialog.tsx:LLM_SETUP_HELP`（让用户设置环境变量后重启 serve）；概览生成弹窗也显示同一段文字。`chat/useAskNotice.ts` 按 provider、模型、源码开关记录首次使用提示，任一变化时重新提示。
- `api/client.ts:send` 只支持 `GET | POST | DELETE`；`ApiError` 带 status 和 code。
- `bridge.ts`：插件注入 `window.codeinsightHost.openFile(path, line)`（插件按自己项目目录打开文件）和 `reviewWorking()`（插件动作“审查未提交改动”让页面审查工作区）。

**JetBrains 插件**（`plugins/jetbrains/`）：以 `serve --repo <projectDir> --exit-on-stdin-close [--data-dir X]` 启动，`ServeInfo` 解析 stdout JSON 的 `port/token/url/repo/dataDir`（`src/test/kotlin/.../serve/ServeInfoTest.kt` 要求 repo、dataDir 是非空绝对路径）。插件始终传 `--repo`，不受 `repo: null` 影响。启动参数在 `src/main/kotlin/dev/codeinsight/idea/serve/ServeProcess.kt:41`（`mutableListOf("serve", "--repo", repo.toString(), "--exit-on-stdin-close")`），`src/test/kotlin/.../runtime/CliEntryTest.kt:84` 检查这组参数，`ServeProcessIntegrationTest.kt` 用真实 CLI 启动 serve。插件的 `openFile(path, line)` 按插件项目目录打开文件，“审查未提交改动”动作也假定页面是项目所在仓库，所以插件里不能切换仓库。serve 的参数解析是 `strict: true`，旧版 CLI 不认识新参数会直接报错退出。

**测试**
- `packages/server/test/helpers/env.ts:openWorkspace` 调 `loadConfig(repo, { dataDir, env: {} })`，只隔离了环境变量；`packages/web/e2e/helpers/cli.ts:cleanEnv` 去掉 `CODEINSIGHT_*`、`ANTHROPIC_*`、`OPENAI_*`；e2e 的 serve 都带 `--repo`、`--data-dir`。另外 `packages/cli/test/process.test.ts:45` 的 `baseEnv` 和 `packages/server/test/mcp.test.ts:47` 的 MCP 子进程环境只给 `PATH` 和 `CODEINSIGHT_LOG`。加了用户设置之后，这些测试默认会读到本机真实的 `~/.codeinsight/settings.json`（可能有真 API Key），serve 子进程还会往真实的最近列表里写临时仓库，必须另外隔离；同一个包的测试文件如果共用一个设置目录，最近列表和设置也会互相影响。
- 各包 vitest 配置：`packages/{core,server,cli}/vitest.config.ts`（有 `globalSetup`）、`packages/web/vitest.config.ts`（jsdom）；e2e：`packages/web/playwright.config.ts`，命令 `pnpm --filter @codeinsight/web test:e2e`，运行前要 `pnpm -r build`。

## 4. 方案设计

### 4.1 整体思路

```
                        ~/.codeinsight/settings.json（权限 600）
                        {llm, autoReindex, recentRepos}
                                   │ core/settings：读写、最近列表
                                   ▼
 环境变量 ─────────► core/config:loadConfig ◄──── <repo>/codeinsight.config.json
                    （用户设置 > 环境变量 > 仓库配置；baseUrl/apiKey 不读仓库配置）
                                   │
          ┌────────────────────────┼─────────────────────── CLI overview / ask / review / mcp
          ▼                        │
 serve 进程（server）              │
   AppContext                      │
   ├ token / staticDir / 设置读写   │
   ├ startup {repo?, dataDir?}     │
   └ repo: RepoContext | undefined ── gen（每次打开仓库加 1）
         ├ ws {repo, config, layout, store}   ← openServerWorkspace()
         ├ indexJobs / reviewJobs / overviewJobs / askRuns / touched
         ├ inflight（进行中的请求数，关闭旧 Store 前等它归零）
         └ changes（工作区内容键检测，节流 10s）
                                   ▲
 Web：GET /api/status（每 5s，带 repoGen、codeChanged）
      所有请求带 X-CodeInsight-Repo: <gen>，过期返回 409 repo_changed
      无仓库 → 选择仓库页；有仓库 → 现有页面（以 gen 为 key 整体重建）
      顶栏：仓库切换 ▾、⚙ 设置（模型服务、自动更新索引）
```

核心原则：

- **一个 serve 同一时间只有一个当前仓库。** 仓库相关的对象全部收进 `RepoContext`，切换就是换一个 `RepoContext`。每个请求在进入路由时取一次 `RepoContext`，整个请求只用它，不会读到一半换了仓库。
- **切换不打断用户的任务。** 有任务在跑时不切换，返回 409 和任务列表；只有能安全中止的（建索引、问答）才提供“取消并切换”。
- **用户设置和环境变量都是用户自己给的，都可信；仓库配置不可信。** 用户设置可以写 baseUrl、apiKey；仓库配置仍然不能。费用和发送相关的上限维持现有规则。
- **API Key 只进不出。** 接口不返回 key 原文，日志不记 key；设置文件权限 600。
- **分析结果按内容复用，更新尽量只算变化的部分。** 内容键相同就整体复用；内容键变了，没变的文件复用提取结果和源码副本；Python 文件都没变时复用调用关系。概览因为花费 LLM 费用，始终手动更新。
- **沿用已有约定**：日志不记 key 和请求体；测试不调真 LLM、不读本机 key 和本机用户设置；函数不超过约 50 行；注释只写功能和设计原因。

### 4.2 数据模型

**用户设置文件** `<CODEINSIGHT_HOME>/settings.json`，`CODEINSIGHT_HOME` 没设时为 `~/.codeinsight`（`os.homedir()`）。目录权限 700，文件权限 600。

```json
{
  "version": 1,
  "llm": {
    "provider": "openai-compatible",
    "baseUrl": "https://api.example.com/v1",
    "model": "gpt-x",
    "apiKey": "sk-..."
  },
  "autoReindex": false,
  "recentRepos": [
    { "path": "/Users/me/projects/clauve", "lastOpenedAt": 1794000000000 }
  ]
}
```

- `llm` 里每一项都可以没有；没有的项按 4.4.2 的顺序从环境变量、仓库配置、默认值取。
- `recentRepos` 按 `lastOpenedAt` 从新到旧，最多 10 个，`path` 是仓库根目录的真实路径（`realpath` 后），重复的合并。
- 读取：文件不存在按空设置；JSON 解析失败或 `version` 不认识时记日志 `user_settings_invalid`、按空设置处理，下一次写入前先把原文件改名为 `settings.json.broken-<时间戳>`，不直接覆盖。单项格式不对（如 provider 不是两种之一、apiKey 不是字符串）时只忽略这一项并记 `user_settings_value_ignored`。
- 写入：读最新内容 → 改对应部分 → `writeFileAtomic(file, json, { mode: 0o600 })`。读到文件权限比 600 宽（有组或其他用户的读写位）时记 `user_settings_permissions` 并 `chmod 600`。Windows 上不检查权限。
- 测试一律设 `CODEINSIGHT_HOME` 指向临时目录（见第 7 节）。

**`extract_cache` 表**（加进 `EXTRA_SCHEMA_SQL`，`EXTRA_TABLES` 加上它，不升 `SCHEMA_VERSION`，沿用“缺表才开事务建表”的做法）

| 字段 | 说明 |
| --- | --- |
| key | 主键。sha1(提取代码指纹 `extractCodeHash()` + path + content_hash + is_test + is_generated)，指纹见 4.4.6 第 5 点 |
| path | 文件路径（清理和排查用） |
| data | 单个文件 `extractPythonFile` 的结果（跨文件识别之前），JSON；`Map` 存成键值对数组 |
| last_used_at | 最近一次被建快照用到的时间 |

清理：`cleanupSnapshots` 结束时删除 `last_used_at` 早于“保留下来的快照里最早的 `last_used_at`”减 1 天的行。

**`snapshot_edges_code` 表**（同样加进 `EXTRA_SCHEMA_SQL` 和 `EXTRA_TABLES`，不升 `SCHEMA_VERSION`）：每个快照一行，记录生成调用边时的代码版本，由提取代码指纹 `extractCodeHash()` 和解析器名称、版本（`Resolver.version`）组成。增量建索引复用上一个快照的调用边前，要求两个快照的这一行相同；不同时照常运行解析器。

**`/api/status` 新增字段**（见 4.3），不改库。

### 4.3 接口设计

所有新接口走现有的 Host / Origin 检查和 cookie / Bearer 鉴权（`server.ts:gate`），不加例外。写入接口在 `ctx.logFields` 记参数，apiKey 只记 `apiKey: 'set' | 'unchanged' | 'cleared'`，baseUrl 只记 origin（`originOf`）。错误体沿用 `{error, message?, ...extra}`。

**仓库标识头**：网页的每个请求带 `X-CodeInsight-Repo: <gen>`。服务端在进入路由前检查：带了这个头且和当前 `gen` 不同（包括当前没有仓库）时返回 409 `repo_changed`，`extra = { repoGen: <当前 gen 或 null> }`。不带这个头的请求（测试、脚本）照常处理。`/api/status`、`/api/repos`、`/api/repo`、`/api/settings*` 不检查这个头。

**需要仓库的接口**：现有的所有 `/api/*` 接口（status 除外）在没有当前仓库时返回 409 `no_repo`。

#### GET /api/status（改）

在现有字段上增加和修改：

| 字段 | 说明 |
| --- | --- |
| repo | 当前仓库根目录；没有仓库时为 `null`，此时下面和仓库有关的字段（index、snapshot、reviews、overview）为 null 或空 |
| repoGen | 当前仓库的 gen（每打开一次仓库加 1，从 1 开始）；没有仓库时为 `null` |
| repoLocked | serve 带 `--lock-repo` 启动时为 true；网页据此隐藏仓库切换入口 |
| dirPickerAvailable | 能弹出系统选择文件夹窗口时为 true（见 `POST /api/repo/pick-dir`）；`--lock-repo` 时为 false |
| llmConfigured、llm、sendSource | 有仓库时按当前上下文的配置；没有仓库时按“用户设置 + 环境变量”（不读仓库配置），sendSource 只看环境变量 |
| snapshot.dirty | 工作区快照的内容键表示有未提交改动时为 true（`workingKeyHasChanges`），提交快照为 false |
| index.job.cached | 已有字段，网页用它显示“复用已有索引” |
| changes | `{ checkedAt: number \| null, codeChanged: boolean, autoReindex: boolean }`：最近一次检测的时间、当前工作区内容键是否和当前快照不同、是否开了自动更新 |

每次处理 status 时，如果距离上次检测超过 10 秒且没有检测在进行，就在后台发起一次检测（不等它完成，返回上一次的结果），见 4.4.5。

#### GET /api/repos

```json
{
  "current": { "path": "/abs/repo", "gen": 3, "dataDir": "/abs/repo/.codeinsight" },
  "startupRepo": "/abs/repo",
  "recent": [{ "path": "/abs/other", "lastOpenedAt": 1794000000000, "exists": true }]
}
```
`current` 没有仓库时为 null；`startupRepo` 是启动时打开的仓库（`--repo` 或当前目录所在仓库，没有为 null）；`exists` 是该路径现在是否还是目录。另有 `locked` 字段，同 status 的 `repoLocked`。

#### POST /api/repo — 打开或切换仓库

请求 `{ "path": "/abs/or/~/path", "cancelRunning": false }`

| 结果 | 响应 |
| --- | --- |
| 打开成功（或与当前仓库相同，不做任何事） | 200 `{ repo, repoGen, dataDir, reused: boolean }`，`reused` 表示与当前仓库相同 |
| serve 带 `--lock-repo` 启动，且目标不是当前仓库 | 409 `repo_locked`（在检查路径之前就拒绝，不探测路径是否存在） |
| path 不是非空字符串、超过 4096 字符、不是绝对路径（`~/` 开头的先展开） | 400 `invalid_param` |
| 路径不存在 / 不是目录 | 400 `path_not_found` / `not_directory` |
| 不在 git 仓库里（`repoRoot` 失败） | 400 `not_git_repo` |
| 新仓库算出的数据目录和当前仓库的相同（如 `CODEINSIGHT_DATA_DIR` 设成了绝对路径） | 409 `data_dir_shared`，message 说明要取消 `CODEINSIGHT_DATA_DIR` 或改成相对路径 |
| 有任务在跑 | 409 `repo_busy`，`extra.tasks = [{kind: 'index'\|'overview'\|'review'\|'ask', id, cancellable}]` |
| 另一个切换正在进行 | 409 `switch_in_progress` |
| 打开新仓库失败（建数据目录、打开库出错） | 500 `internal_error`（详情只写日志），当前仓库不变 |

`cancelRunning: true` 时：在跑的任务全部 `cancellable`（只有建索引、问答）就先取消再切换；有不能取消的（概览、审查）仍返回 409 `repo_busy`。

日志：`repo_switch_start {from, to, cancelRunning}`、`repo_switch_rejected {code, tasks}`、`repo_switched {from, to, gen, ms}`、`repo_context_closed {repo, gen, waitedMs}`。

#### POST /api/repo/pick-dir — 弹出系统选择文件夹窗口

请求体为空。服务端在本机弹出系统原生的选择文件夹窗口，等用户选完后返回；只返回路径，不打开仓库（网页拿到路径后填进输入框，用户点“打开”再走 `POST /api/repo`）。

| 结果 | 响应 |
| --- | --- |
| 选中 | 200 `{ status: 'selected', path: '/abs/dir' }`（去掉末尾 `/`） |
| 用户取消 | 200 `{ status: 'cancelled' }` |
| 已有一个窗口没关 | 409 `picker_busy` |
| `--lock-repo` | 409 `repo_locked` |
| 平台不支持或找不到命令 | 409 `picker_unavailable` |
| 超过 5 分钟没选 | 结束弹窗进程，200 `{ status: 'timeout' }` |
| 命令异常退出（非取消） | 500 `picker_failed`（详情只写日志） |

实现（`server/src/dir-picker.ts`）：

- 全部用 `execFile`（不经 shell），参数固定，不拼接用户输入；超时 5 分钟；同一时间只允许一个弹窗（模块内标记，结束时清除）；客户端断开时结束弹窗进程。
- macOS：`osascript -e <脚本>`。脚本先 `tell application "System Events" to activate` 让窗口显示在最前面，再 `POSIX path of (choose folder with prompt "选择要分析的仓库")`。第一次运行时系统可能要求授权控制 “System Events”；用户拒绝时 osascript 报错 -1743，改为不带 activate 的 `choose folder` 再执行一次（窗口可能在浏览器后面）。用户点取消时 osascript 以错误 -128（“User canceled”）退出，按 cancelled 处理。
- Linux：按顺序找 `zenity`（`--file-selection --directory --title=...`）、`kdialog`（`--getexistingdirectory <home>`）；退出码 1 且无输出按取消处理。
- Windows：`powershell -NoProfile -STA -Command`，脚本 `Add-Type -AssemblyName System.Windows.Forms; $d = New-Object System.Windows.Forms.FolderBrowserDialog; if ($d.ShowDialog() -eq 'OK') { $d.SelectedPath }`；输出为空按取消处理。
- `dirPickerAvailable`：serve 启动时检测一次——macOS 有 `osascript`；Linux 有 `DISPLAY` 或 `WAYLAND_DISPLAY`，且 PATH 里找得到 `zenity` 或 `kdialog`；Windows 找得到 `powershell`；并且没有 `--lock-repo`。
- 执行弹窗命令的函数 `runPicker(cmd, args, {timeoutMs, signal})` 和可用性检测都通过 `AppContext.dirPicker` 注入，测试换成假实现，不在 CI 里真弹窗。
- 日志：`dir_picker_start {platform, command}`、`dir_picker_done {status, ms}`（选中时记路径）、`dir_picker_failed {exitCode, error}`。

#### GET /api/settings

- `shadowed`：某项环境变量也设了值、但被用户设置盖住时列出来，网页提示“环境变量 X 也设置了，当前使用用户设置”。

#### POST /api/settings/llm — 保存模型服务设置

请求 `{ "provider": "anthropic", "baseUrl": "", "model": "", "apiKey": "", "clearApiKey": false }`

- `provider`：必填，`anthropic` 或 `openai-compatible`。
- `baseUrl`：空字符串或不传表示不在用户设置里保存（用环境变量或默认）；非空时必须是 `http:` / `https:` 的 URL、不含用户名密码、不超过 2048 字符，保存时去掉末尾 `/`。
- `model`：空表示不保存；非空不超过 200 字符、不含换行。
- `apiKey`：空或不传表示**不改**；非空时不超过 4096 字符、不含空白字符。`clearApiKey: true` 表示从用户设置删掉 key（之后用环境变量的 key，没有就是未设置）。
- 400 `invalid_param` 写明哪一项。
- 成功：写设置文件；有当前仓库时用新设置重新 `loadConfig`（`dataDir` 固定为当前上下文的数据目录）并替换 `ws.config`；返回和 GET 相同的结构。
- 日志 `user_settings_saved {provider, baseUrlOrigin, model, apiKey: 'set'|'unchanged'|'cleared'}`。

`{"port":..,"token":"..","url":"..","repo":null,"dataDir":null}`：只有“没传 `--repo` 且当前目录不在 git 仓库里”时 repo、dataDir 为 null；传了 `--repo`、或当前目录在 git 仓库里，和现在一样是绝对路径。

#### serve 的启动参数（改）

- `--repo`：去掉默认值 `'.'`。传了按现在的规则打开（不是 git 仓库时报错退出，和现在一样）；没传时对当前目录调 `repoRoot`，成功就打开它（和现在不传时的结果相同），失败（不在 git 仓库里）就以“无仓库”启动，stderr 输出一行 `no git repository at <cwd>; choose one in the web UI`。
- `--lock-repo`：锁定启动时的仓库，必须同时有当前仓库（传了 `--repo` 或当前目录在 git 仓库里），否则参数错误退出。锁定后 `POST /api/repo` 切到别的仓库返回 409 `repo_locked`，status 返回 `repoLocked: true`。设置接口不受影响。

### 4.4 关键流程

#### 4.4.1 用户设置读写（core/settings）

```ts
export function codeinsightHome(env = process.env): string        // CODEINSIGHT_HOME 或 ~/.codeinsight
export function userSettingsPath(env = process.env): string
export async function readUserSettings(opts?: { path?: string }): Promise<UserSettings>
export async function updateUserSettings(change: (s: UserSettings) => UserSettings, opts?): Promise<UserSettings>
export async function touchRecentRepo(repo: string, opts?): Promise<void>   // 放到最前，超过 10 个丢掉最旧的
export async function removeRecentRepo(repo: string, opts?): Promise<void>
```

- 位置只看**进程环境变量** `process.env.CODEINSIGHT_HOME`，不看 `loadConfig` 的 `opts.env`：`opts.env` 是测试用来隔离 LLM 变量的，设置文件位置是进程级的；测试统一在 vitest 配置和 e2e 子进程环境里设 `CODEINSIGHT_HOME`。
- `updateUserSettings` 每次写前重新读文件，减少多个 serve 进程之间互相覆盖的范围。
- 读设置出错（权限不足等）时 `loadConfig` 记日志并按空设置继续，不让所有命令起不来。

#### 4.4.2 配置合并（core/config）

`loadConfig(repo, { dataDir, env, userSettings })`：`userSettings` 不传时调 `readUserSettings()`；传 `null` 表示不读（测试和内部用）。

LLM 各项的取值顺序：

| 项 | 顺序 |
| --- | --- |
| provider | 用户设置 > `CODEINSIGHT_LLM_PROVIDER` > 仓库配置 `llm.provider` |
| model | 用户设置 > `CODEINSIGHT_LLM_MODEL` > 仓库配置 `llm.model` > anthropic 默认模型 |
| baseUrl | 用户设置 > `CODEINSIGHT_LLM_BASE_URL` > 默认（客户端内置） |
| apiKey | 用户设置 > `CODEINSIGHT_LLM_API_KEY` > 按生效的 provider 取 `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` |

- 仓库配置里的 `llm.baseUrl`、`llm.apiKey`、`llm.apiKeyEnv` 仍忽略并给 `config_llm_key_ignored`，规则不变。
- `resolveLlm` 改成返回每项的值和来源（`llmSources`），`loadConfig` 用值，`GET /api/settings` 用来源；同一个函数，两边不会不一致。没有仓库时传空的仓库配置。
- `sendSource`、snippets、并发、确认阈值、问答上限的规则不变；用户设置里不放这些项。
- `dataDir` 的规则不变（命令行 > `CODEINSIGHT_DATA_DIR` > 仓库配置 > 默认）。

#### 4.4.3 仓库上下文与打开仓库（server）

```ts
interface RepoContext {
  gen: number;
  ws: ServerWorkspace;                // config 可被设置接口替换
  indexJobs: IndexJobs; reviewJobs: ReviewJobs; overviewJobs: OverviewJobs; askRuns: AskRuns;
  touched: Map<number, number>;
  inflight: number;                    // 进行中的 HTTP 请求数
  changes: ChangeDetector;             // 4.4.5
  closing: boolean;
}
interface AppContext {
  repo: RepoContext | undefined;
  startup: { repo?: string; dataDir?: string };
  nextGen: number;
  switching: boolean;
  staticDir?: string;
  openWorkspace: (repo: string, dataDir?: string) => Promise<ServerWorkspace>;  // 默认 openServerWorkspace，测试可注入
}
```

- `RequestContext` 增加 `repo?: RepoContext`。`dispatch` 在匹配到路由后：检查 `X-CodeInsight-Repo`；路由声明 `needsRepo`（默认 true）时取 `app.repo`，没有就 409 `no_repo`；`repo.inflight++`，响应 `close` 时 `--`。路由里 `ctx.app.ws`、`ctx.app.indexJobs` 等全部改为 `ctx.repo!.ws`、`ctx.repo!.indexJobs`（提供 `repoOf(ctx)` 取非空值）。
- `openServerWorkspace(repo, { dataDir, resolver })`（`server/src/workspace.ts`）：`repoRoot` → `loadConfig` → `initDataDir` → `checkPyrightExclude`（提示写日志 `pyright_exclude_hint`）→ `new Store`。CLI 的 `openWorkspace` 改为调用它，再把 pyright 提示写 stderr。
- `createRepoContext(app, ws)`：建各任务对象，`gen = app.nextGen++`。任务类构造函数里“把中断的 running 记录改 failed”改为**每个 serve 进程对同一个数据目录只做一次**：`AppContext.recoveredDataDirs: Set<string>`，第一次打开某个数据目录时调用 `failInterrupted()` / `failInterruptedReviews()`，切回同一仓库时不再调用（构造函数改为不自动执行，由 `createRepoContext` 决定）。这两个方法本身都只改 pid 已不存在的记录，CLI 进程正在跑的概览和审查不会被改；只做一次是为了避免 `failInterruptedReviews` 把“pid 等于本进程”的记录误标失败。然后 `indexJobs.start('startup' | 'switch')`、 `touchRecentRepo(ws.repo)`（失败只记日志）。
- 保活定时器改为每次触发时取 `app.repo?.indexJobs.touchCurrent()`。
- `startHttpServer` 的 `workspace` 改为可选：传了就作为启动仓库建上下文（行为同现在）；不传就没有当前仓库。`RunningHttpServer` 去掉没人用的 `indexJobs`、`reviewJobs`、`overviewJobs` 字段，换成 `app()`（测试用，返回当前上下文）。
- 关闭服务：`close({drain})` 对当前上下文做原来的 drain，然后关闭它的 Store（现在由 CLI 的 `stop` 关闭，改为 server 负责，因为切换后 CLI 拿不到新的 Store）。

#### 4.4.4 切换流程

```
POST /api/repo {path, cancelRunning}
  0. app.locked（--lock-repo）且 path 不是当前仓库（只做字符串和 realpath 比较）→ 409 repo_locked
  1. 检查参数，展开 ~，stat；repoRoot(path) → root（失败 400）
  2. root 与当前仓库相同 → 200 reused
  3. app.switching 为 true → 409 switch_in_progress；否则置 true（finally 里复位）
  4. dataDir = root 与 startup.repo 相同时用 startup.dataDir，否则 undefined（默认规则）
  5. ws = await app.openWorkspace(root, dataDir)          // 只建新对象，不碰旧的
     ws.config.dataDir 与当前仓库的 dataDir 相同 → 关闭 ws.store，409 data_dir_shared
  6. tasks = runningTasks(app.repo)
     有任务：
       - cancelRunning 且全部可取消：取消（见下），等它们结束，回到第 6 步再检查一次
       - 否则关闭 ws.store，409 repo_busy {tasks}
  7. （同步，中间没有 await）再查一次 runningTasks 为空 → old = app.repo；app.repo = createRepoContext(ws)
  8. 返回 200；后台：old.closing = true，等 old.inflight 归零（最多 10s）和 old 的 drain，然后 old.ws.store.close()
```

- `runningTasks(ctx)`：`indexJobs.runningJob()`（新增，返回在跑的任务；类里已有私有字段 `running`，方法不用这个名字）、`overviewJobs.runningId`（私有字段改名后加只读 getter）、`reviewJobs.activeIds()`（新增，`start` 时记 id，结束时删）、`askRuns.activeSessions()`（新增）。
- 取消问答：`askRuns.drain()`（回答保存为 cancelled，原因 `repo_switch`）。
- 取消建索引：`indexJobs.cancel('repo_switch')`。`IndexJobs` 每个任务有自己的 `AbortController`，把 `signal` 传给 `buildSnapshot`（见 4.4.6 第 8 点），`cancel` 调 `abort` 后 `await job.done`。中止在任何阶段都有效：复制和读文件、提取期间在每个文件之间检查，最长等一个文件的处理时间；scip-python 运行中由 runner 结束子进程。任务状态记为 `failed`，`error: 'cancelled'`。不再用进程级的 `killActiveScipProcesses()`。被取消的快照：提取已入库的留下 `resolver_status=failed`（`resolver_error: 'cancelled'`），下次打开这个仓库时 `buildOrReuse` 只重跑解析；提取还没入库的留下 `extract_status=pending`，下次由 `startSnapshot` 清空重建。
- 第 7 步检查和替换在同一个同步块里，期间不会有新任务插进来；第 5、6 步的 await 期间新开始的任务会在第 7 步被查到并拒绝（关闭新 ws）。
- 等 `inflight` 归零是为了不在别的请求还在用旧 Store 时关闭它（比如正在读源码、估算概览的请求）；超过 10 秒仍未归零就记 `repo_context_close_timeout` 后关闭，这些请求会以 500 结束。
- 旧上下文的 `touched`、变化检测都随它丢弃。

#### 4.4.5 代码变化检测与自动更新

`ChangeDetector`（`server/src/changes.ts`，每个 `RepoContext` 一个）：

- `maybeCheck()`：由 status 调用。距离上次开始检测不到 10 秒、或已有检测在进行时直接返回。否则后台执行：`resolveRef(root, 'HEAD')` + `workingContentKey(root, head, excludeDirs(config, root))`，和 `indexJobs.current()?.contentKey` 比较，记下 `{checkedAt, workingKey, codeChanged}`。出错（如 git 被别的进程锁住）记 `change_check_failed`，结果保持上一次。
- 当前快照还没建好、或有建索引任务在跑时不检测（结果为 `codeChanged: false`）。
- 自动更新：`autoReindex` 打开、`codeChanged` 为 true、连续两次检测得到**同一个** `workingKey`（代码至少 10 秒没再变，避免边写边建）、没有建索引任务在跑、这个 `workingKey` 上次自动更新没有失败过时，`indexJobs.start('auto')`，日志 `index_auto_start {workingKey}`。失败的 key 记在内存里，不反复重试。
- `autoReindex` 由 `readUserSettings` 读取，设置接口保存后通知当前上下文刷新。
- 只有网页在轮询时才检测；没有网页打开时不检测（本次不做后台定时检测）。
- 概览不自动生成：新快照建好后 `overviewStale` 为 true，网页显示已有的“更新概览”提示。

#### 4.4.6 增量建索引（core/snapshot）

现在每次内容键变化都会：复制全部支持语言的文件 → 从工作区再读一遍全部文件 → 解析全部 Python 文件 → 对整个快照跑 scip-python。改为：

1. **找上一个快照**：`store.listSnapshots()` 里同类型（工作区或提交）、`extract_status=ok` 且快照目录还在的最近一个（`previousSnapshot`），取它的 `files` 行（path → content_hash）。没有就全部按新文件处理。
2. **读文件、写快照目录**（合并现在的 `prepareWorking` 和 `readFiles`，只读一遍）：对清单里每个文件读出内容、算 sha1；需要放进快照目录的文件（支持语言和项目配置）：
   - 与上一个快照同路径同 hash，且上一个快照目录里的文件存在且不是符号链接 → `link(prev, dest)`（硬链接）；失败（跨文件系统、旧目录刚被清理）就写入刚读出的内容；
   - 否则写入刚读出的内容；符号链接仍按 `copyEntry` 复制链接本身。
   这样快照目录里的内容和库里的 `content_hash` 一定一致（现在先复制后读，文件在中间被改过时两者可能不一致）。提交快照仍用 `exportArchive`，不做硬链接（导出本身就是从 git 对象写文件）。
3. **按文件复用提取结果**：每个 Python 文件按 4.2 的 key 查 `extract_cache`；命中就反序列化，没命中就 `extractPythonFile` 并在跨文件识别之前序列化写入缓存。缓存里存的是跨文件识别之前的结果，然后对全部文件照常跑 `resolveDjangoEntries` 和 `resolveModels`（这两步只在内存里做，代价小）。所以结果和全量提取在构造上相同：同样的输入、同样的函数，只是省掉了没变文件的解析。
4. **调用关系**：
   - 这次放进快照目录的全部文件（路径、hash、符号链接目标）和上一个快照完全相同、上一个快照 `resolver_status=ok` → 不跑 scip-python，把上一个快照的 `edges` 用 `INSERT INTO edges SELECT ... WHERE snapshot_id = ?` 复制过来，`resolver_status=ok`，`resolver_error` 沿用，日志 `resolve_reused {fromSnapshot}`。这覆盖“只改了 README、SQL、模板等非 Python 文件”的情况。
   - 否则仍对整个快照目录跑 scip-python。**scip-python 不做增量**：它是对整个项目做类型推断（`scip-python index --cwd <快照目录>`，见 `core/src/scip/runner.ts:81`），没有只处理部分文件的模式；而且一个文件的改动会影响其他文件里调用的解析结果（改了函数签名、改了类继承、改了 import），只重跑改动文件得到的调用边不正确。
5. **缓存失效**：不靠手工改版本号。key 里放“提取代码指纹” `extractCodeHash()`（`core/src/extract/cache.ts`）：进程内第一次用到时，读取指纹清单里全部模块文件，按相对路径排序后求 sha1，再拼上 `tree-sitter-python`、`web-tree-sitter` 的包版本（语法版本变了解析结果会变），结果在进程内缓存。模块文件按运行时位置读取（以 `new URL('..', import.meta.url)` 为根，构建后是 `dist/**/*.js`，vitest 下是 `src/**/*.ts`）。提取相关代码只要有改动（包括本地开发时改源码），指纹就变，旧缓存自然不命中。
   - 指纹清单：`extract/` 目录下全部模块，加上 `extract/` 引用的、会影响缓存内容的目录外模块 `model/symbol-key.ts`（`extract/python.ts` 用 `makeSymbolKey`、`symbolIdFromKey` 生成的符号 key 和 id 会进缓存）和 `util/collections.ts`。这两个文件没有再引用其他项目模块。
   - 不进指纹的白名单（只放不影响缓存结果的模块）：`log.ts`（只写日志）、`model/types.ts`（只有类型，编译后没有运行时代码）。
   - 已核实 `extract/*.ts` 引用的目录外模块只有这四个：`../log.js`、`../model/symbol-key.js`、`../model/types.js`、`../util/collections.js`。
   - `is_test`、`is_generated` 进 key，改了 `testGlobs` 也会失效。
   - 测试：`extractCodeHash(root)` 接受根目录参数，对临时副本里 `extract/python.ts`、`model/symbol-key.ts` 各改一个字节后指纹都不同，只改 `log.ts` 时指纹不变；另有一条测试扫描指纹清单里各文件的 import（递归），发现引用了既不在指纹清单、也不在白名单里的项目模块时失败，提醒把它加进清单。
6. **清理**：见 4.2；快照目录被清理时，硬链接指向的内容仍被新快照持有，不受影响。
7. **日志**：`extract_done` 增加 `cacheHits`、`cacheMisses`；`snapshot_copied` 增加 `linked`、`written`；新增 `resolve_reused`、`snapshot_build_cancelled {contentKey, stage}`。
8. **中止信号**：`BuildSnapshotOptions.signal?: AbortSignal`。检查点：读文件和写快照目录的循环里每个文件之间、提取循环里每个文件之间、`saveExtraction` 之后、`runResolver` 之前；已中止就抛 `SnapshotCancelledError`（带当前阶段）。`runResolver` 之前发现中止时把快照标 `resolver_status=failed`、`resolver_error='cancelled'` 再抛出；`Resolver.resolve` 的输入加 `signal`，`ScipPythonResolver` 传给 `scip/runner.ts:runProcess`，中止时结束子进程并删临时输出（复用已有的结束逻辑）。等快照锁时也响应中止。`IndexJobs` 把 `SnapshotCancelledError` 记为 `failed / cancelled`。CLI 的 `index`、`review` 不传 signal，行为不变。

“同一仓库再次打开不从头分析”在现有代码里已经成立：内容键相同就整体复用快照（`reusable()`），概览从 `overviews` 表读最近一次，模块划分和 LLM 缓存在重新生成时复用。本次补上的是：网页上显示出来（4.4.7），以及内容键变化后只做必要的工作（本节）。

### 4.6 备选方案

- **多个仓库同时打开（每个仓库一个上下文，URL 或请求头带仓库 id）**：不选。所有现有接口和网页状态（当前快照、概览、会话）都要带仓库维度；多个仓库的建索引（scip-python 很吃 CPU 和内存）、概览可能同时跑；鉴权 cookie 按端口区分，多个仓库共享同一个 token。需求只要求“在网页里指定要分析的仓库”，一次一个仓库已经满足，复杂度低很多。需要同时看两个仓库时可以启动两个 serve。
- **切换时启动一个新的 serve 子进程、网页跳转到新端口**：不选。cookie 按端口，跳转后要重新登录（token 要再传给网页）；插件拿不到新端口；进程管理复杂。
- **浏览器原生的目录选择（`<input type="file" webkitdirectory>`、File System Access API 的 `showDirectoryPicker`）**：不选。浏览器出于安全不把绝对路径给页面（只有目录名或文件句柄），而服务端要的是本机绝对路径；`webkitdirectory` 还会把整个目录的文件列表读进页面。
- **服务端提供目录浏览接口、网页里画目录树**：不选。用户不需要；还要处理权限、符号链接、大目录分页，并且等于把本机目录结构通过接口暴露出去。系统原生窗口更熟悉，也不增加接口面。
- **API Key 存系统钥匙串**：更安全，但要引入原生依赖或调用 `security` 等命令，跨平台成本高；本次用权限 600 的文件，与 `~/.aws/credentials`、`~/.npmrc` 等常见做法一致。
- **用户设置放进仓库的数据目录**：不选。设置是用户级的，换仓库要重新配；数据目录在仓库里，误提交的风险更大。
- **环境变量优先于用户设置**：更符合“环境变量临时覆盖文件配置”的习惯，但网页保存后如果环境变量里有值就不生效，用户会困惑。已确认采用“用户设置优先”，环境变量被盖住时网页显示 `shadowed` 提示。
- **切换后整页刷新（`location.reload()`）代替按 key 重建组件**：实现同样简单，但会闪一下，插件里 JCEF 刷新还会重新注入 JS 桥；按 key 重建只重置页面状态，cookie 和连接都不受影响。
- **增量提取直接复制上一个快照的 `symbols`、`entries` 行**：不选。模型类判断和 Django 路由是跨文件的，改了一个文件里的基类，没改的文件里子类的 `model_kind` 也会变；复制行之后还要补算这些，而补算需要的 `classes`、`imports` 等信息库里没有。缓存跨文件识别之前的单文件结果，再整体跑一遍跨文件识别，结果和全量一致，容易验证。
- **增量提取只用进程内缓存**：serve 重启后第一次建索引就失效，CLI 命令（`index`、`review`）也用不上；存在库里的 `extract_cache` 表对所有命令和重启都有效。
- **快照目录用 APFS 克隆（`COPYFILE_FICLONE`）代替硬链接**：只在 macOS APFS 上省空间和时间，Linux 常见文件系统上退化成复制；硬链接在同一文件系统上都可用，且失败时可以退回写入。

## 5. 兼容性与上线

- **`--repo` 不传时**：当前目录在 git 仓库里时和现在完全一样；只有原来会报错退出的情况（当前目录不在 git 仓库里）改为以“无仓库”启动。usage 文字更新。
- **插件**：始终传 `--repo`，stdout JSON 不变；`--data-dir` 对启动仓库照常生效。新版插件加 `--lock-repo`，网页里看不到切换入口。新插件配旧版 CLI 时，旧 CLI 不认识 `--lock-repo` 会报错退出：插件读到 serve 以“unknown option”类错误退出时，去掉 `--lock-repo` 重启一次并记日志（旧 CLI 本来也没有切换功能，不锁定也没有影响）。旧插件配新 CLI：不带 `--lock-repo`，网页会显示切换入口，切换后插件里点击符号可能打不开文件，在发布说明里提示升级插件。
- **配置优先级变化**：之前只用环境变量的用户不受影响（没有设置文件）。在网页保存过设置后，环境变量里同名项被覆盖，网页上有 `shadowed` 提示，说明当前使用用户设置。
- **库结构**：只新增 `extract_cache` 表（`CREATE TABLE IF NOT EXISTS`），不升 `SCHEMA_VERSION`；旧版本 CLI 打开新库时忽略这张表，不会删库重建。
- **回滚**：回到旧版本时 `~/.codeinsight/settings.json` 被忽略，配置回到只读环境变量；`extract_cache` 表留着无害。
- **数据目录**：切换到的仓库按默认规则在仓库里建 `.codeinsight/`（带 `.gitignore`）。`CODEINSIGHT_DATA_DIR` 设成绝对路径时，切换到别的仓库会因为数据目录相同被拒绝（409 `data_dir_shared`），避免两个仓库共用一个库。

## 6. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 测试读到本机真实的 `~/.codeinsight/settings.json`（含真 key） | 测试调用真 LLM、泄露 key 到日志；serve 子进程往真实最近列表写临时仓库；测试之间互相影响 | 每个测试文件由 vitest `setupFiles` 设一个新的临时 `CODEINSIGHT_HOME`；每个子进程（`cli/test/process.test.ts`、`server/test/mcp.test.ts`、cli 的 serve 测试、e2e 的每个 serve）各建一个临时目录传进去；core 测试检查读取路径来自 `CODEINSIGHT_HOME`；e2e 结束后检查临时目录外没有新写的 settings.json |
| API Key 写进日志或返回给网页 | key 泄露 | 设置接口只返回 `set` 和 `last4`；日志只记 `apiKey: set/unchanged/cleared`；server 测试检查响应体和日志输出里都不含 key 原文 |
| 设置文件权限过宽 | 本机其他用户读到 key | 写入用 mode 600，读到更宽的权限时改回 600 并记日志；目录 700 |
| 切换时旧 Store 被关闭，仍有请求在用 | 这些请求 500 | 进入路由时计数，等计数归零（最多 10 秒）再关闭；网页的请求带仓库标识，切换后旧标签页的请求直接 409 |
| 旧标签页请求里的快照 id 在新仓库的库里也存在 | 读到别的仓库的数据，或在新仓库发起错误的审查 | `X-CodeInsight-Repo` 检查，gen 不同时 409 `repo_changed` |
| 检查任务和替换上下文之间有新任务开始 | 新任务写进即将关闭的库 | 第 7 步在同一个同步块里再查一次并替换，中间没有 await |
| 取消建索引后旧快照留下 `resolver_status=failed` 或 `extract_status=pending` | 下次打开该仓库要重跑解析 | 现有 `buildOrReuse` 已处理（只重跑解析）；网页在“取消并切换”按钮旁说明 |
| 测试连接把已保存的 key 发到表单里新填的 baseUrl | key 被发到用户填错的地址 | 这是用户自己的操作；网页在 baseUrl 改过且 apiKey 留空时提示“将使用已保存的 key 测试这个地址”；接口要求鉴权，别的网页调不到 |
| 多个 serve 进程同时写设置文件 | 最近列表或设置被后写的覆盖 | 每次写前重新读；原子改名保证文件完整；最近列表丢一项影响很小 |
| 变化检测在大仓库里耗时 | status 变慢、git 进程多 | 后台执行、不阻塞 status；每 10 秒最多一次、同时只有一个；页面不可见时不轮询 |
| 自动更新索引在用户编辑过程中反复触发 | CPU 占用高 | 默认关；要求连续两次检测得到同一个内容键；同时只跑一个建索引任务；失败的内容键不重试 |
| 增量提取缓存过期（提取逻辑改了但缓存没失效） | 符号、入口和全量结果不一致 | key 含提取代码指纹（对 `extract/` 模块文件内容求 hash，不靠手工改版本号）和 tree-sitter 包版本；指纹清单含 `extract/`、`model/symbol-key.ts`、`util/collections.ts`，有测试检查清单里的模块没有引入清单和白名单以外的项目模块；阶段 2 的测试比较增量和全量结果；`CODEINSIGHT_CLAUVE` 集成测试在 clauve 上比较 |
| 复用调用边的条件判断错（Python 文件实际变了却复用） | 调用关系错误 | 比较的是放进快照目录的全部文件（含项目配置和符号链接目标），不只是 Python 文件；测试覆盖改 Python 文件、改 `pyproject.toml`、只改 README 三种情况 |
| 硬链接指向的文件被就地修改 | 旧快照内容跟着变 | 快照目录里的文件只由建快照写入（scip-python 输出写在 `scip/` 的临时文件），写入新文件一律先删再写，不就地修改；测试检查改工作区文件后旧快照目录内容不变 |
| 仓库根目录正好是用户主目录 | 数据目录 `~/.codeinsight` 和设置目录相同 | 文件名不冲突（`settings.json` vs `index.db` 等），不做特殊处理；在风险里记录 |

## 7. 测试方案

**core 单测**
- 用户设置：`CODEINSIGHT_HOME` 决定路径；不存在按空设置；写入后文件权限 600、目录 700（非 Windows）；读到 644 的文件会改成 600；JSON 损坏时按空设置并在下次写入前改名为 `.broken-*`；单项格式不对只忽略这一项；最近列表去重、按时间排序、最多 10 个、`removeRecentRepo`。
- `writeFileAtomic` 的 `mode`：新文件和覆盖已有文件后权限都是指定值。
- 配置合并：用户设置 > 环境变量 > 仓库配置（provider、model 各一组用例）；baseUrl、apiKey 用户设置 > 环境变量，仓库配置里的仍被忽略并有 `config_llm_key_ignored`；apiKey 按生效的 provider 取 `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`；`llmSources` 的 source 和 `shadowed`；`userSettings: null` 时和现在行为一致（已有 config 测试不改期望值）；sendSource 等上限的已有用例不改期望值。
- 增量建索引（用 py-basic、py-shop fixtures 和假 resolver）：
  - 同一仓库连续两次改动后建快照，增量结果与关闭缓存的全量结果逐行一致（files、symbols、entries、edges 去掉 snapshot_id 后排序比较）；
  - 跨文件：只改基类所在文件，没改的文件里子类的 `model_kind` 跟着变；只改视图文件，没改的 urls.py 产生的 Django 入口仍正确；
  - 缓存命中数：第二次只改一个文件时 `cacheMisses = 1`；改 `testGlobs` 后相关文件不命中；
  - 硬链接：没变的文件和上一个快照目录里的文件 inode 相同；改工作区文件后旧快照目录内容不变；上一个快照目录被删掉时退回写入；

  - 库：旧库（没有 `extract_cache` 表）打开后自动加表，原数据还在。
